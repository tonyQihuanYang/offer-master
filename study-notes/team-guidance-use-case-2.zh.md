# 团队辅导：实时反作弊检测（Use Case 2）

> **对应面试题：**
> 一个 4 人团队（每人 2-3 年经验）在用 Kafka + Flink 做骑手行为的实时反作弊检测。处理延迟 45 秒，目标是 <5 秒；scope 蔓延（3 → 12 个模式）；数据质量未知；没有明确测试策略；3 天后 sprint review，无可演示内容；团队士气低。Staff 工程师的角色是**给技术指导，但不替他们做事**，并且与 Tech Manager **协作**（不是取代他）。

这份文档的写法，是 Staff 工程师走进这个局面之前会准备的内容。它覆盖面试题列出的全部五个考察维度（诊断、辅导策略、3 天行动、长期培养、与 TM/Principal 协作），并回答这道题真正在测的元问题：**这个候选人能否成为 force multiplier，而不替团队完成工作？**

---

## 核心原则

**真正的危机是 deadline，不是架构。** 团队 3 天后要 demo，但手上什么都没有。最大的诱惑——也是 Staff 最常见的失败模式——是走进去、重新设计架构、写关键路径代码、把这个 sprint 给"救"出来。这能解决 demo，但**毁掉团队**。他们会学到一件事：每当事情不顺，Staff 工程师就会出现并把他们绕过去。

正确的做法更难：**争取时间、缩小 scope、用诊断的方式辅导，让团队自己交付一个他们真正理解的东西。** 那些架构性的问题（Flink 是不是合适的工具？数据模型对不对？）放在 sprint review **之后**回答，不是之前。

第二条原则同样重要：**那个想"换个简单方案重来"的工程师，可能是对的。** Staff 工程师会认真对待这个建议，而不是把它当成"我们已经在 Flink 上投入这么多了，不能现在掉头"来拒绝。有时候简单方案就是正确答案，**早一点意识到这一点**也是这份工作的一部分。

---

## 这里"Staff 角色"和 Tech Manager 的边界

面试题明确把这一点列出来了。把这条边界画对，已经是答案的一半。

| 关注点 | Tech Manager 负责 | Staff Engineer 负责 | 共同 |
|---|---|---|---|
| sprint scope、deadline | ✓ | | 帮 TM 把技术理由说清楚 |
| stakeholder 谈判（PM、leadership） | ✓ | | 提供技术框架 |
| 个人绩效、职业发展 | ✓ | | 提供技术信号 / 上下文 |
| 团队士气 | ✓ | | 浮出"技术挫败"层面的原因 |
| 架构 | | ✓ | |
| 测试策略 | | ✓ | |
| 知识转移 / mentorship | | ✓ | TM 给资源 |
| RFC、设计评审 | | ✓ | |
| Sprint review 的对外表述 | | | ✓ 共同起草、TM 主讲 |
| 升级处理 | | | ✓ 一起去找 leadership |

要避免的陷阱：**踏进 Tech Manager 的角色**（去和 PM 谈判、单方面决定 scope、自己去解决士气问题）。TM 拥有你没有的授权；在不和他协调的情况下行使他的权限，既削弱他的位置，也让团队感到困惑。

互补面：**不要在你不在的时候让 TM 来做技术决定。** 在这次紧急期间，架构决策要走你这条路，而不是在 TM 和 PM 的私聊里被拍板。

任何 engagement 的前 30 分钟，应该是和 Tech Manager 的 1:1，把上面这条边界画清楚。

## 问题 1 —— 诊断与评估

目标：**在不诱导回答的前提下**，把根因浮出来。团队会给你症状（"Flink 慢"）；你的工作是用问题把症状变成根因。

### 架构诊断（45 秒延迟问题）

| 问题 | 浮出的内容 |
|---|---|
| "在白板上把端到端的数据流走给我看一遍。" | 看团队是否有共享的心智模型。常常没有。 |
| "45 秒具体花在哪一段——ingest、processing、sink，还是别的？这是测出来的还是推断的？" | 强制"先量再优化"。很多"Flink 慢"实际上是"在某个 operator 里同步调了 DB"。 |
| "每个分区峰值事件率多少？parallelism 设的多少？" | 抓出"hot key 没充分并行"——这是流处理延迟的头号原因。 |
| "watermark / event-time 怎么设的？late event 在堆积吗？" | 抓出 event-time 配置错误，看起来像处理慢。 |
| "operator 里有 I/O 吗——DB 查询、HTTP 调用？同步还是异步？" | 抓出 blocking I/O，这是 Flink 的反模式。 |
| "checkpoint 时长多少？有没有 backpressure？" | 抓出 checkpoint storm 和反压级联。 |
| "Flink 是不是真的适合我们当前事件率？测过吗？" | **大问题**。50K 骑手 × 每天约 30 单 = 每天约 150 万事件 = 平均约 20 events/sec、峰值约 100/sec。Flink 的设计目标是 100k+ events/sec。团队可能在为根本用不到的容量付复杂度税。**（注意：UC2 没给体量。~20/秒**只数了送达事件**；欺诈靠的 GPS ping 可能把它推到 ~1,000–3,000/秒，而 UC1 的 2M offers/hr ≈ 556/秒 也说明平台本就在几百/秒。所以真实量级可能在 ~20 到几千/秒之间——**先测（尤其 GPS）再下"过度设计"的结论**。）** |

### Scope 诊断（3 → 12 模式问题）

| 问题 | 浮出的内容 |
|---|---|
| "12 个模式中，stakeholder 这个季度最想要的是哪 3 个？" | 强制做没做的优先级排序。 |
| "每个新模式是谁、什么时候决定要在**这个** sprint 里上的？" | 经常浮出"决策是在某次 1:1 里拍的，团队没参与"。 |
| "如果模式 N 不在这个 sprint 上、放到下一个 sprint 上，成本是什么？" | 大多数"必须有"其实不是。 |
| "如果只交付最初的 3 个，系统还能交付那个核心业务结果吗？" | 通常答案是"能"。剩下 9 个是"加分"伪装成"关键"。 |

### 数据质量诊断

| 问题 | 浮出的内容 |
|---|---|
| "缺失位置数据的事件占多少百分比？按骑手 / 按城市的分布？" | 把问题量化。"有些"是无法行动的；"CH 的 12% 事件"是。 |
| "'缺失'具体指什么——字段为 null、用了默认值、过期、完全没传？" | 不同的失败模式需要不同的应对。 |
| "上游可以修吗，还是我们只能在下游处理？" | 决定这是"修一次"问题还是"永久处理"问题。 |
| "位置缺失时的正确行为是什么——丢弃、标记可疑、deadletter、等晚到的？" | 浮出从未明说的业务规则。 |

### 测试诊断

| 问题 | 浮出的内容 |
|---|---|
| "现在端到端测一条作弊规则是怎么测的？演示一下。" | 经常浮出"没有 fixture、没有 replay 能力"。 |
| "你们有已知作弊和已知正常事件的语料库吗？" | 没有标注数据集，就没法测 precision / recall。 |
| "改一条规则后的反馈循环是多长——秒、分、还是小时？" | 长反馈循环会扼杀迭代速度。 |
| "有没有写过一个集成测试，输入固定、断言输出？" | 让差距诚实地浮出来。 |

### 团队 / 士气诊断

这些最好和 TM 协作处理，但你需要这些答案才能在技术上决定怎么走：

| 问题 | 在哪里问 |
|---|---|
| "每个工程师**个人**觉得最被卡住的是什么？" | 理想情况下 TM 做 1:1；如果不行，简短的小组"现在最难的是什么"。 |
| "那个想'换个方案重来'的工程师——他具体想换成什么？" | 直接对话。他的视角是有信息量的。 |
| "团队最初对这个 sprint 'definition of done' 的理解是什么？" | 通常和 PM 现在的理解不一样。把两个版本都写下来。 |

### 关键的 Staff 动作：**问题分波次提出**

不要一次性把 30 个问题砸下去。分波次：

```
第 1 波（15 分钟）："带我走一遍你们建的东西，告诉我哪里卡住了。"
第 2 波（边听边问）：针对他们提到的 1-2 件事做精准追问
第 3 波（会后）：和"想重来"的工程师、和最卡住的工程师分别 1:1
```

这些问题是**诊断仪器**。用对了，能让团队学会怎么思考，而不只是知道答案。

## 问题 2 —— 不替团队解决问题的辅导策略

这道题最难的部分。资深工程师在这种情况下的本能是**自己上手修**——他们能看见答案。Staff 的动作是**让团队自己看见答案**。

### 有效的辅导动作

| 技巧 | 实际样子 |
|---|---|
| **结对编程，不替写** | 坐在工程师旁边一起 debug。问"指标显示什么？""如果把这里的 parallelism 翻倍会怎样？" 让他敲键盘。 |
| **白板讲原理，不讲解决方案** | "我们一起画一下这个系统里的反压长什么样" → 而不是"修法是在 operator 之间加一个 Kafka topic"。 |
| **用 code review 当教学界面** | 评论用**问句**："如果这个 map 是 null 会怎样？" 而不是"加一个 null check"。 |
| **帮他们写 RFC（让他们写）** | 他们写文档。你在评论里追问。文档变成持久资产 + 技能锻炼。 |
| **带进第二意见** | 安排一次 30 分钟的 review，邀请熟悉流处理的 Principal。让**团队**讲，不是你讲。 |
| **给阅读清单，不给 TL;DR** | DDIA 第 11 章（Stream Processing）；Akidau 的 Streaming Systems 第 1-3 章；Flink 的 Concepts 文档。一起读，下一次会上讨论。 |
| **借外部的声音说敏感的话** | 如果"Flink 不合适"这个结论真的成立，团队接受这个结论的最好方式，往往是他们自己在 workshop 上得出，而不是你直接告诉他们。 |

### 失败的辅导动作

| 反模式 | 为什么失败 |
|---|---|
| **自己写修复代码** | 解决了 demo，毁掉了团队。他们学到的是"你是答案机器"。 |
| **"用 X 替换 Flink"作为判决式宣告** | 他们在 Flink 上花了几周。单方面推翻读起来就是"你浪费了我们的时间"。 |
| **长篇流处理理论讲座** | 2-3 年经验的工程师已经听够了讲。他们靠**做**学。 |
| **拒绝给任何直接答案** | 反向失败。如果他问"checkpoint duration 一般用 ms 还是 s 衡量？"——直接答"通常是 ms"。藏着事实不是辅导。 |
| **在 stakeholder 面前公开纠正** | 信任会崩。**私下纠正，公开表扬**。 |

### 一个具体例子：那 45 秒延迟

工程师：*"45 秒延迟我怎么修？"*

**Senior 的回答**："大概是反压。在 operator 里加 async I/O，把 keyed stream 的 parallelism 翻倍。"

**Staff 的回答**："延迟分布看起来怎样——哪一步最慢？" → （工程师回答） → "指标显示这一步发生了什么？" → （工程师给假设） → "我们怎么验证这个假设？" → "好，跑一下这个实验。结果会告诉我们什么？"

终点一样，**路径不同**。Staff 版本教的是**调试方法**；Senior 版本教的是**症状到修复**的对应关系。

## 问题 3 —— 3 天紧急行动计划

这一节里最重要的 Staff 动作：**冷酷地决定什么是 demo 得了的，把其他的都锁出 scope。** 团队真正的问题不是"我们交付不了 12 个模式"，而是"我们要交付 12 个，但其实 1 个就足以讲清楚故事"。

### Day 1（今天）

**上午（30-90 分钟）**

| 活动 | 产出 |
|---|---|
| 和 Tech Manager 1:1 | 边界对齐；缩 scope 的方案达成一致；谁去和 PM 沟通也定下来 |
| 60 分钟架构走查（团队主导） | 共享心智模型；写下来的瓶颈清单（**他们的**清单，不是你的） |

**中午（60 分钟）**

| 活动 | 产出 |
|---|---|
| 和 TM、团队、PM 一起开 scope-lock 会 | demo 范围锁定为**一个**模式。其余 11 个推后。**PM 书面同意。** |

这是 3 天里**最关键的决策**。挑**最简单**的、还能展示架构的反作弊模式：例如"骑手在距离目的地 >500m 处标记送达"。它需要的：
- delivery-complete 事件里的位置（已有）。
- 目的地位置（已有）。
- 一个距离计算（trivial）。
- 输出到一个 sink（alert / table / log）。

无论用不用 Flink，端到端 <5 秒都是做得到的。

**下午（剩余时间）**

| 活动 | 产出 |
|---|---|
| 在 demo 路径上结对（工程师敲键盘，你提问） | Day-1 可跑的骨架——哪怕慢，但能跑通 |
| 单独：把"demo 之后"的架构关切写下来 | 不是这个 sprint。留给回顾用。 |
| 和团队一起写"demo 定义"文档 | 一页：要演示什么，不演示什么，原因 |

### Day 2

| 活动 | 产出 |
|---|---|
| 继续在 demo 路径上结对 | 端到端用 fixture 测过 |
| 写一个小的测试 fixture（5-10 条事件，覆盖正负样本） | 第一个**可测试**的资产——会比 demo 活得更久 |
| 和 TM 一起起草 sprint review 叙事 | 诚实表达："我们在 [流处理 + 数据质量] 上撞到了未预期的复杂度，主动 descope，这是能跑通的部分，下一步路径在这里" |
| 和"想重来"的工程师做一次安静的 1:1 | 听完。他大概率有**真信号**。把内容收好留给回顾。 |
| 帮 TM 给 stakeholder 做预沟通 | TM 把新 scope 提前告诉 PM 和高层 stakeholder。**会议现场不应该有意外。** |

### Day 3（sprint review 准备）

| 活动 | 产出 |
|---|---|
| 30 分钟 dry run（团队讲） | 他们讲，你看。打磨表达。 |
| 和 TM 一起预报 Director | leadership 听到 descope 是从工程 + TM 这里听到的，不是从 PM 现场听到的 |
| 安排下周的 post-demo 回顾 | 架构再评估、scope 讨论、知识缺口 |

### Sprint review 当天

你坐在台下。**团队上台**。TM 主导 descope 叙事。你在那里，是为了在出现需要资深架构语言的提问时支持——但**功劳归团队**。

如果会上 leadership 质疑团队，你和 TM **一起**站出来："这次 descope 是工程层面的主动判断，背景在这里，下一步路径在这里。" 永远不要让团队**单独**面对一个有敌意的升级现场。

### "demo 得了"具体是什么意思

sprint review 三种可接受的结果，按偏好递减：

1. **完整可跑的流式 demo**，单一模式、端到端、<5 秒。哪怕没在生产规模。
2. **批处理 demo + 流式包装** ——"下个 sprint 我们切换到流式，这是固定数据集上的检测"。**对差距诚实**。
3. **架构评审演示** ——"我们发现架构和实际数据量不匹配，下一步方案是这个，原因是这些"。**高风险**；只有在 1 和 2 都真的不可能时才用。

**要避免**：一个跑一半失败的流式 demo。团队会为此沮丧好几周。

## 问题 4 —— 长期团队培养（知识转移）

这是**防止下一次 3 天危机**的部分。没有它，两个月后你又会回到这个房间。

### 30 天

| 活动 | 节奏 | 为什么 |
|---|---|---|
| 流处理基础 study group | 每周 2 小时 × 4 周 | 共享词汇 + 基线心智模型 |
| DDIA 第 11 章、Streaming Systems 第 1-3 章、Flink Concepts 文档 | 会前自读 | 自学 + 小组讨论 = 留得住 |
| 邀请外部流处理工程师做 2 次分享（公司内专家 或外聘） | 每次 90 分钟 | 外部声音讲常见陷阱 |
| 架构 office hours | 每周 1 小时 | "不在危机中"也能问"我该怎么…"的固定窗口 |

### 60 天

| 活动 | 为什么 |
|---|---|
| 每位工程师在生产代码之外做一个小 Flink toy（如带 windowing + late event 的 word count） | 实际动手；安全的失败空间 |
| 团队基于学到的内容写 v2 RFC | 浮出剩余知识缺口；演练 RFC 技能 |
| 一起 code-read 另一个团队的 Flink 真实任务 | 把"生产 Flink 代码"去神秘化 |

### 90 天

| 活动 | 为什么 |
|---|---|
| 每位工程师向团队讲一个流处理概念（windowing / watermark / exactly-once / state / backpressure） | 教是最高形式的学。**他们现在拥有这块知识了。** |
| 识别出团队内一位流处理专家 | 团队内可持续的专家点 |
| 与有流处理经验的另一团队建立长期 review 配对 | 网络效应；减少对你的依赖 |

### 关键原则：**不要让他们在隔离中学**

如果公司里有运营生产流处理系统的团队，**和他们结对**——code review、联合架构会、嵌入式工程师一个月。**跨团队知识转移比团队内自学快得多。** 你作为 Staff 的工作，是去**搭这条桥**。

## 问题 5 —— 与 Tech Manager 和 Principal 协作

这是面试题明确点出的问题。本文档开头那张边界表是框架。下面是它在实际中怎么落。

### 与 Tech Manager（你的 peer）

**紧急期间的节奏：** 每天 15 分钟 check-in。紧急期过后改为每周 1:1。

**长期约定：**

| 事项 | 约定 |
|---|---|
| 架构决策 | 走我；TM 不在我不在时单独 approve |
| Scope 决策 | TM 拥有；我提供技术框架 |
| 给工程师的个人反馈 | TM 拥有职业层面的对话；我提供技术信号 |
| Sprint review 表述 | 共同起草，TM 主讲 |
| 给 Director 的升级 | 联合简报；**一起进会议室** |
| 公开批评我到来之前的决策 | **不做**。承认约束。向前看。 |

**要避免：**

- 绕过 TM 直接给工程师下指令。**永远把 TM loop 进来。**
- 让工程师把 TM 和你互相挑拨（"但 Staff 说…"）。**立即浮出并制止。**
- 把团队的恢复成果归功于自己。**团队恢复，你建议。**

### 与 Principal（你的资深 peer 或上级，取决于公司层级）

**用他们做：**
- **架构第二意见** —— 在决策**锁定之前**带他们进来，不是失败之后。
- **模式匹配** —— 他们见过这种危机。问"你见过 Flink-是-错-工具 的局面吗？怎么收的尾？"。
- **示范升级行为** —— 你不确定怎么处理 leadership 时，先问 Principal。
- **技术硬决策的兜底** —— 如果团队或 TM 推回你的建议，Principal 复审能 confirm 或修正。

**不要用他们做：**
- 替你干活。他们是资源，不是挡箭牌。
- 越过你的 TM。Principal 是技术输入，不是政治后盾。

### 与 leadership（PM 正在升级的对象——Director / VP）

**抢在 PM 升级前面。** 在 leadership 从一个挫败的 PM 那里听到 sprint 没完成之前，你和 TM 联合简报：

```
"我们发现：团队为一个（按我们测得的量级）远低于 Flink 设计点的工作负载选了 Flink，
现在在为复杂度税付出 shipping 速度的代价。我们已经主动 descope 这个
sprint 来交付一个模式；接下来 30 天我们会正式评估架构是否需要变更。
团队会在 [日期] 给出建议。我们希望你在我们做这件工作的时候给 PM 提供
air cover。"
```

一个好的 leadership 简报应该具备：
- **对哪里出错保持诚实** —— 但表述为工程判断，不是甩锅。
- **具体的时间线** —— leadership 下一次什么时候听到、听到什么。
- **具体的 ask** —— "air cover"是真实的 ask；"支持"不是。
- **联合** —— TM 和 Staff 一起。**不是其中一个。**

## 最难的几个时刻怎么走

### 时刻 1：工程师让你"直接把修改写一下"

回应：*"我可以和你一起结对做。我们一起做——我宁愿你真的搞懂这块，因为以后是你 on call 它。"* 坐在他旁边。**他敲键盘。**

### 时刻 2：TM 提议交付 12 个全部模式以让 PM 满意

回应（**私下**对 TM 说）：*"如果我们交付 12 个半通的模式，下个月我们会回到这个房间，问题更糟。我宁愿现在就在 descope 这件事上扛压力，也不要以后在质量上扛。和 PM 沟通这件事我支持你。"*

### 时刻 3：PM 直接问你能不能给一个交付日期

回应：*"我想给你一个真实的答案。让我下午和 [TM] 同步一下，明天我们带着一个站得住脚的日期回来。"* **永远不要在 TM 不在时当场承诺日期**，特别是当你正想支持 TM 的时候。

### 时刻 4：团队士气崩溃，一个工程师快要离职

这是 **TM 的领域**，不是你的。你的角色：把你观察到的浮给 TM（"我注意到 [工程师] 看起来已经放弃了——想让你知道"）；提供技术侧支持（多结对一些；减少他在 demo 路径上的负载）。**不要主导士气对话**——这是 TM 的工作，那个工程师需要的是 TM，不是 Staff。

### 时刻 5：那个"想重来"的工程师其实是对的

最坏情况：你调研下来确认 Flink 真的不合适。怎么走？

**这其实是团队的胜利**——只要表述对了：
1. **公开**夸那个工程师："[工程师] 早就指出来了——我们应该更早地认真对待。"
2. 把 Flink 上的工作描述为**没浪费**：它浮出了数据质量问题、scope 问题、真实事件率。**没有这些工作**，团队就会基于同样错误的假设建 v2。
3. 拥有这个学习："回头看，**应该在选工具之前先量事件率**。这是给下一次架构决策的教训。"

团队从这个局面中走出来时**比之前更有能力**，不是更弱。**这才是 Staff 辅导真正产出的东西。**

## 要避免的反模式

| 反模式 | 为什么失败 |
|---|---|
| **走进去自己重写架构** | 解决 demo，毁掉团队。 |
| **因为工具选型批评团队** | 他们选 Flink 是因为有人告诉他们"流处理 = Kafka + Flink"。是组织的模式库失败了，不是反过来。 |
| **拒绝给出任何技术建议、说"我需要更多数据"** | 到了某个点你**必须**给指导。光诊断不开方就是瘫痪。 |
| **越过 TM 找 leadership** | 对工作关系是灾难性的。**哪怕你是对的。** |
| **在 sprint review 上公开纠正** | **公开表扬，私下纠正。** |
| **把"想重来"的工程师当成问题** | 他在提供数据。当 peer 来对待。 |
| **假装知道自己不知道的事** | 在 Staff 这一级，"我不知道——我们一起去搞清楚"是力量的标志。 |
| **对 12 个模式都点头以显得好相处** | 团队会默默地失败，并且会因为你没替他们扛而对你失望。 |
| **不写下来** | 你在这个房间里做的决定**必须活得过这场会议**。ADR、RFC、会议记录。 |

## 各类会议中的具体话术

**诊断阶段：**
- *"帮我搞清楚——你说 Flink 慢，具体测过什么？"*
- *"什么样的数据能让你认为 Flink 是错的工具？什么样的数据能让你认为它是对的？"*
- *"12 个模式里，你**个人**觉得最重要的是哪 3 个？"*

**辅导阶段：**
- *"你对这件事发生的原因有什么假设？"*
- *"我们怎么验证它？"*
- *"如果非要赌，你赌最可能的原因是什么？"*
- *"我可以直接告诉你答案，但我更希望你自己找到——你会先试什么？"*

**与 TM 的边界：**
- *"这是 scope 决策——我得确保 [TM] 在这个对话里。"*
- *"我可以讲技术风险；优先级决策是 [TM] 的。"*

**与工程师的边界：**
- *"我和你结对，但你敲键盘。"*
- *"我希望你拥有这件事——你需要我做什么？"*

**Sprint review 表述：**
- *"我们基于工程判断主动 descope。这是已交付的部分，这是我们学到的，下一步路径在这里。"*
- （在 leadership 质疑时）*"这是正确的判断。我会再做一次同样的判断。"*

## 收尾姿态（一句话落地）

回答 Use Case 2 的那一句话：

> *"我在这里的角色，是让团队**自己变得更擅长这件事**——而不是替他们做。这个 3 天 deadline 是一个要导航的约束，不是一个要表演的舞台。如果我做对了，这个团队下一次做流处理项目时，**不需要 Staff 工程师来当救火队员**。"*

这句话抓住了 Staff 的核心区分：**长期的杠杆，而不是当下的英雄主义。**

- **力量倍增器 vs 救火队员** → "收尾姿态"

## 建议的 25 分钟面试节奏

| 时间 | 章节 | 要交付什么 |
|---|---|---|
| **0–3 分** | Frame | "危机是 deadline，不是架构。" 与 TM 的边界。 |
| **3–8 分** | 诊断问题 | 走完架构 / scope / 数据质量 / 测试 / 团队五个 bucket。**不**列全部 30 个问题——每个 bucket 挑 2-3 个，解释**为什么**那个问题是诊断性的。 |
| **8–15 分** | 3 天计划 | Day 1 / Day 2 / Day 3 / sprint review。**descope 决策和 demo 定义是承重动作。** |
| **15–18 分** | 辅导技巧 | 那个 worked example（45 秒延迟）。结对而不替写。 |
| **18–22 分** | 长期 + 知识转移 | 30/60/90 计划。跨团队结对。 |
| **22–25 分** | 与 TM/Principal 协作 | RACI 表。联合 leadership 简报。"想重来"的工程师可能是对的。 |

如果被问到"那 Flink 的架构问题具体是什么？"——简短回答（按测得量级远低于 Flink 设计点，复杂度税；但要点明 GPS ping 量级须实测，可能高 1–2 个数量级），然后**回到** "但我在这里的工作不是宣告它错——是帮团队**自己量出来、自己得出**这个结论"。
