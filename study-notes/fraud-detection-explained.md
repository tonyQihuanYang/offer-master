# 实时欺诈检测是怎样运作的（UC2 学习笔记）

> English version: [`../en/fraud-detection-explained.md`](../en/fraud-detection-explained.md)
>
> 配套可运行教学 demo：[`../flink-kafka-lab/`](../flink-kafka-lab/)（`node flink-kafka-lab/run.mjs`）。
> 本文把"引擎怎么跑"（Flink）和"检测怎么运作"（fraud detection）合在一起讲，是 UC2 的复习笔记。

## 一句话

> **持续地从快递员的行为事件里算出"风险信号"，再按信号分级触发"响应"，并用人工复核的结果反过来让它越来越准。**
> Flink 只是中间"算"的那一环；完整系统是一条 **事件 → 风险信号 → 响应 → 反馈** 的闭环。

## 第一部分：引擎怎么跑（Apache Flink）

### 最大的误区

教学 demo 是"一个进程、跑一次、跑完退出"。**真实 Flink 不是脚本，是一个常驻的分布式集群**——一堆长期运行的 JVM 进程，你的 job 提交后 **7×24 永远在跑**，不停从 Kafka 拉数据、处理、输出。它不像批处理"跑完就结束"。

### 集群组成

```
   Client ──submit job──▶  ┌─────────────────────────────────┐
   (打包好的 JAR/Python)    │  JobManager  (大脑/协调者)        │
                           │   - 把 job 拆成并行任务            │
                           │   - 调度、协调 checkpoint、故障重启 │
                           └──────────────┬──────────────────┘
                                          │ 调度
                        ┌─────────────────┼─────────────────┐
                        ▼                 ▼                 ▼
                   ┌─────────┐       ┌─────────┐       ┌─────────┐
                   │TaskMgr1 │       │TaskMgr2 │       │TaskMgr3 │  (工人)
                   │ slot... │       │ slot... │       │ slot... │
                   └────┬────┘       └─────────┘       └────┬────┘
                        │ 拉数据                            │ checkpoint
                        ▼                                   ▼
                    Kafka (源)                        S3 / HDFS (状态快照)
```

| 角色 | 干嘛的 |
|------|--------|
| **Client** | 把打包好的 job 提交给集群，然后就能走 |
| **JobManager** | 大脑：把 job 变成并行任务、调度到 worker、协调 checkpoint、故障时从快照重启 |
| **TaskManager** | 工人：真正跑算子代码的进程；每个有几个 **slot**（=能并行跑几个任务）|

### job 怎么变成"在跑的东西"

1. 你写的 source → operator → sink 其实是一张**数据流图**。
2. 提交后，JobManager 按**并行度(parallelism)**把每个算子拆成多个**并行子任务**。
   - `parallelism=4` → keyBy 算子有 4 个副本，跑在 4 个 slot 上（可能在不同机器）。
3. `keyBy(courierId)` 触发一次 **shuffle**：同一 courier 的所有事件路由到固定子任务 → 这个 courier 的状态只存在那个子任务里。
4. job **永远在跑**，常驻消费 Kafka。

### 让它活下来的核心：Checkpoint

1. 每隔几秒，所有子任务**同时给状态拍一致快照**，存到 S3/HDFS。
2. 某个 TaskManager 崩了 → Flink 从最近快照恢复状态 + **回拨 Kafka offset** → 重放。
3. 结果：**精确一次(exactly-once)**——崩溃也不丢、不重。

> demo 里的 `KeyedState`（一个 JS Map）崩了就全没了；真实 Flink 靠 checkpoint 让它能在机器挂掉后原样复活。这是单进程脚本和分布式流引擎的本质差距。

### 实际怎么"运行 Flink"

- **自建集群**：Docker/K8s 起 JobManager + TaskManagers，`flink run yourjob.jar`。
- **托管服务**（省运维）：AWS Kinesis Data Analytics for Flink / Confluent / Ververica。
- **本地玩**：`./bin/start-cluster.sh`，打开 `localhost:8081` Web UI 看 job 图、并行度、checkpoint、背压。

## 第二部分：检测怎么运作（端到端）

```
① 行为事件          ② 管道(Flink)         ③ 决策          ④ 响应              ⑤ 反馈
─────────          ──────────────         ──────         ──────             ──────
GPS 定位      ─┐                          风险评分        低 → 只记录          分析师判定
送达事件       ├─▶ Kafka ─▶ 富化 ─▶ 检测 ─▶ (0~1 或    ─▶ 中 → 进人工复核队列 ─▶ (确认/误报)
收入/支付      │            (补目的地/     (规则+ML)     标记)          高 → 自动动作        │
商家/订单     ─┘             商家/画像)                                (扣发/暂停/复验)      │
                                                                                          ▼
                                                              ◀──── 标注数据回流:调阈值 / 重训模型
```

### ② 检测——怎么"判"

| 手段 | 怎么判 | 优缺点 |
|------|--------|--------|
| **规则 (rules)** | 写死阈值：距离>500m、速度>200km/h、每分钟>5 单 | ✅ 快、透明、好解释；❌ 死板，绕得过 |
| **ML 模型** | 学"正常长什么样"，偏离打高分（异常检测/分类），输出 0~1 风险分 | ✅ 抓微妙的串通；❌ 要标注数据、难解释 |
| **混合** | 规则抓明确的 + ML 抓微妙的 → 合成一个**风险分** | 实战主流 |

> lab 里的三条规则就是"规则"档：`far-from-dest`（无状态）、`fake-gps`（有状态）、`high-rate`（窗口）。串通这种微妙的才需要 ML。
>
> 三类算子复习：**无状态**（一条事件就够判断）/ **有状态**（要 keyed state，比如和上一条 ping 比）/ **有状态+窗口**（按时间聚合计数）。

### ④ 判出来之后怎么"做"（最容易被忽略的一环）

**关键：不是直接封号。** 误判会伤到好快递员，所以**按置信度分级响应**：

| 风险 | 动作 |
|------|------|
| 低 | 只记录 / 监控 |
| 中 | **进人工复核队列**——运营分析师看一眼 |
| 高 | 自动动作：暂扣这单结算 / 暂停账号 / 要求重新验证 |

> **Human-in-the-loop（人工在环）是核心**。高风险动作要么走人工，要么先"软处置"（扣发不封号）等复核——因为"GPS 飘了 2km"很可能只是信号差，不是欺诈。

### ⑤ 怎么"越来越准"（闭环）

1. **Shadow mode（影子模式）**：新规则/模型先**只算不动作**，拿历史已知结果对比，测准了再上线。
2. **反馈环**：分析师的"确认欺诈 / 误报"判定 → 变成**标注数据** → 调阈值、重训模型。
3. **两个核心指标的权衡**：
   - **Precision（精确率）**：标记的里面有多少真欺诈（高 = 少冤枉好人）
   - **Recall（召回率）**：真欺诈里抓住了多少（高 = 少漏网）
   - 阈值调高 → precision↑ recall↓；调低反之。**业务定平衡点。**

## 走一遍：一个可疑事件的完整旅程

```
快递员在离目的地 2.2km 处点"已送达"
   └─▶ DELIVERY_COMPLETE 事件(带 GPS) ─▶ Kafka
        └─▶ Flink:补上这单目的地坐标 ─▶ far-from-dest 规则:2224m > 500m ✓
             └─▶ 产出风险信号(中置信度)
                  └─▶ 策略:暂扣这单结算 + 进人工复核队列
                       └─▶ 分析师看轨迹:商场地下信号差 → 判"误报" → 释放结算
                            └─▶ 误报回流 → 调高该区域阈值 / 给模型加特征
```

## 对应到 lab 和 UC2

- **lab 做的是 ②检测 这一环**——`alert(...)` 就是产出"风险信号"，到此为止。
- **真实系统在 alert 之后还有 ③决策→④响应→⑤反馈**（评分、复核队列、扣发、重训）。
- **UC2 的团队**卡在②的流式实现上；但完整 fraud 系统远不止流式。**Staff 的辅导**：先把**最简单一条规则端到端跑通**（检测→告警），证明链路，再逐步加 ML、加响应、加反馈——别一上来就 12 个模式 + ML + 自动封号全都要。
- **right-sizing——但先测量（UC2 没给体量）。** 这个数完全取决于*你数哪些事件*：
  - *只数送达事件：* 5 万快递员 × 每天约 30 单 ≈ **~20/秒平均、~100/秒峰值**。
  - *加上 GPS ping*（欺诈检测真正吃的信号）：~1 万人同时在线、每 ~5 秒上报一次 ≈ **~1,000–3,000/秒峰值**——高 1–2 个数量级。
  - *交叉验证：* UC1 的 **2M offers/hour ≈ 556/秒**（持续），说明平台本就跑在几百/秒量级。
  - 所以欺诈相关的真实量级很可能在 **~20 到几千/秒** 之间——这个区间**横跨"Flink 过度"和"Flink 合理"**。**别断言过度，先测真实事件率（尤其 GPS 量），再 right-size**：低端 → Kafka 消费者 + Redis；高端 → Kafka Streams / Flink。无论哪种，45 秒延迟多半是配错（同步 I/O / 并行度不足 / 热 key / checkpoint 风暴），和选型无关。

## 到底什么时候才真需要 Flink？（不只看吞吐）

光看吞吐量决定不了。真正的问题是你是否撞上下面这些**质变触发器**——撞上了，即使量不大流引擎也值；没撞上，几千/秒也能用 Kafka 消费者 + KV 存搞定。

| 触发器 | "保持简单"（消费者 + DB/KV） | "Flink / Kafka Streams 划算" |
|--------|------------------------------|------------------------------|
| **1. 实时聚合 / 窗口状态** | 只查单条记录的当前状态 | 需要"过去 X 分钟"——滚动计数、按 geo-hash 的需求热力图、内存里算 surge 信号毫秒级触发 |
| **2. Event-time & 乱序/迟到** | 按服务器收到时间算就行 | 信号差区域的事件迟到/成批到，必须按**事件真正发生的时间**归窗（正确的结算窗口）——需要 event-time + watermark |
| **3. 实时模式匹配 (CEP)** | T+1 跑批第二天找出作弊者 | 必须在**作弊过程中**拦截——比如同一骑手 1 分钟内出现在相距 5km 的两点——在付款前 |
| **4. 会压垮 DB 的聚合** | MySQL 加索引 / 读写分离扛得住 | GPS 写入已经压力大，再在上面 `GROUP BY`/`SUM` 会锁库——在流里按"国家/城市/分钟"算好，只把**结果**写库 |

外加：**exactly-once + 大的容错状态**（结算级准确，崩溃后必须精准续接）。

> **所以判断是两段式的：**（a）测真实事件率（尤其 GPS），（b）看你撞上了哪个触发器。撞上 → Flink（或更轻的 Kafka Streams）**即使吞吐不高也值**；一个都没撞上 → **即使几千/秒也保持简单**。**只凭骑手数就断言"已达 Flink 门槛"——没有实测量级、也没有触发器——正是要避免的陷阱（两个方向都是）。**（注：15 个国家跨时区会把高峰**摊开**，降低瞬时并发——国家多 ≠ 峰值高。）

## 一句话总结

> **fraud detection = 流式地从行为事件算风险信号（规则+ML），按置信度分级响应（记录/人工复核/自动处置），再用复核结果闭环调优。Flink 是常驻分布式集群、只是"算"的那一环；真正难的是分级响应不误伤好人、和让系统越来越准的反馈环。**
